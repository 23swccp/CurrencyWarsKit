# 货币战争 CLI：AI 游玩模式设计

更新日期：2026-11-02  
文档状态：设计草案，供后续开发与评审使用。技术路线已确定为 **Python + MaaFramework**，尚未开展实机兼容性验证。本文中的 `m7a cw ...` 是拟新增接口，不代表当前项目已经实现。

项目定位：独立的货币战争 AI 控制工具，能够独立启动和使用，也可供其他项目通过公开接口接入。三月七小助手是潜在接入方，不是运行前提。本文中 `m7a cw ...` 是早期设计示例，尚未确定为独立程序的实际命令名；独立程序应有自己的入口，最终名称和命令格式待设计确认。

**阅读和施工约定：**本文同时保留整体流程和具体动作设计。动作清单用于确定范围；只有写明前置条件、执行步骤、成功与失败判断、异常处理，并经实际游戏验证的动作，才具备可靠实现依据。标记为「待实机确认」的内容是待验证的设计，不是已知游戏事实；不能由开发者或 AI 自行猜测并写成确定规则。

交互时序、界面状态和动作流程图见[设计图索引](design/README.md)。其中 `see` 和高级动作是接口草案，当前使用 `screenshot` 查看游戏画面。

## 1. 项目目标与最小原则

开发独立的「货币战争 AI 游玩模式」工具，支持与三月七小助手集成。外部 AI 阅读规则、策略文档和当前局势，决定如何游玩；程序负责识别、定位、执行和验证。

与现有固定策略模式并列：

```text
固定策略模式：程序里的预设策略决定下一步，程序执行。
AI 游玩模式：外部 AI 决定下一步，程序执行。
```

遵守以下原则：

1. **先封装常见操作，减少 AI 的机械工作。** AI 可以表达「给这个角色装备这件物品」，不用逐次打开菜单、找坐标、拖动和确认结果。
2. **异常接管是独立能力。** 常规封装无法继续时，AI 仍能查看截图、文字与坐标，通过基础操作修复界面。
3. **用槽位指代目标。** 第一版不引入角色实例 ID、装备实例 ID、复杂对象关系。
4. **只增加必要字段。** 不重复返回同一事实，不为将来可能出现的需求提前设计大量字段。
5. **程序返回事实，AI 作玩法决策。** 费用、位置、星级等事实不能被策略优先级覆盖。
6. **先搭可验证的框架，再适配新版内容。** 素材、布局和规则独立维护；改版若改变交互或流程，还需修改对应操作适配。
7. **功能完整的前提下，代码能少则少。** 优先采用直接、易理解的实现；不为假设中的需求提前增加抽象、配置、依赖或重复代码。必要的输入校验、结果验证、异常处理和可读性不能为了减少代码而省略。
8. **文件名、函数名等命名简洁规范。** 名称准确表达职责，使用项目统一风格；不使用冗长的重复前缀、无意义缩写或难以理解的单字母名称。优先让用户能根据名称找到并理解代码，而不是单纯追求字符最少。

## 2. 职责边界

### 2.1 AI 负责

- 选择模式、难度和本局目标。
- 判断开局是否接受，选择投资环境、投资策略、补给和遭遇挑战。
- 决定买卖角色、刷新商店、购买经验、阵容和站位。
- 决定装备分配、合成、道具使用以及角色特殊选项。
- 根据经济、生命值和战斗表现调整策略。
- 处理程序没有覆盖的界面或执行异常，决定继续、重规划或放弃。

### 2.2 程序负责

- 截图、OCR、模板匹配，读取界面与局势。
- 将角色头像、装备图标等转换成名称和槽位。
- 执行已指定意图所需的机械步骤。
- 检查动作条件，等待画面稳定，验证操作结果。
- 监测战斗、收集无需选择的掉落、读取结算。
- 保证游戏输入串行执行，保存必要的日志和异常现场。
- AI 修正界面后，重新识别并恢复到可继续的位置。

首版建议使用游戏自带自动战斗，AI 负责局外运营和节点选择。逐回合技能、目标与终结技操作不作为首版目标。

### 2.3 封装操作的停止边界

程序可以完成一次已明确的意图，但不能在过程中擅自作新的玩法选择。

例如「给前台第1格装备库存第2件物品」：

```text
定位物品 → 定位角色 → 执行穿戴 → 验证
                               │
                               └─ 出现替换装备等新选择 → 返回选项，交给 AI
```

纯机械确认可以包含在动作内部；会选择新目标、额外花钱、出售角色或改变策略的确认，需要原指令明确涵盖，否则交回 AI。

## 3. 简洁的运行架构

```text
外部 AI
  │ 读取文档、执行命令
  ▼
轻量 CLI
  │ 本地 HTTP + JSON
  ▼
Python 常驻执行程序
  ├─ 当前观察
  ├─ 货币战争局势整理、动作参数与结果验证
  ├─ AI 接管、基础操作与恢复控制
  └─ MaaFramework 适配
       ├─ Controller：窗口截图、鼠标和键盘
       ├─ Resource：识别模型、模板和小型 Pipeline
       └─ Tasker：提交识别、动作和短任务，读取执行结果
  ▼
游戏
```

- CLI 每次调用都可启动和退出，只负责参数解析、通信和输出。
- 执行程序在控制会话期间常驻，复用识别模型、游戏连接和运行状态。
- 业务代码主要使用 Python，底层识别与控制使用 MaaFramework 运行库。
- 本地 HTTP 可用 Python 标准库实现，客户端可用 `urllib.request`。
- 服务仅监听本机地址。端口、进程信息和访问凭据由程序管理，CLI 自动读取。
- 第一版只控制一个游戏窗口、同一时间执行一个操作。并发请求不得造成输入重叠。
- 不引入外部消息队列、数据库或模型调用框架。日志和必要状态采用普通文件保存。
- 本地 HTTP 接口层可跨平台；首版先验证 MaaFramework Win32 控制器，其他平台和云游戏需要分别验证。
- Windows 运行任务所需的提权在执行程序启动时完成，后续命令复用已有进程。
- AI 模式持有游戏操作权，避免与固定策略任务同时运行。

外部 AI 主动调用 CLI；普通 CLI 服务本身不会主动唤醒 AI。

### 3.1 Python 与 MaaFramework 的分工

| 部分 | 职责 |
|---|---|
| Python CLI／服务 | 命令解析、HTTP、JSON、运行记录 |
| Python 游戏逻辑 | 将识别结果整理成槽位与局势，检查动作条件与业务结果 |
| MaaFramework Controller | 统一完成截图、点击、拖动、按键等基础交互 |
| MaaFramework Resource／识别 | 加载 OCR 模型、图片素材、识别配置与 Pipeline |
| MaaFramework Tasker | 执行短任务或独立识别／动作，报告运行与失败情况 |
| Python 自定义扩展 | 处理不能方便地用配置表达的识别和动作逻辑 |

正常封装和 AI 兜底输入都通过同一个受控的 MaaFramework 适配出口，保持输入串行。框架执行成功不直接等于游戏动作成功；购买、部署、穿戴等仍要检查实际业务结果。

第一版直接使用 Python 绑定和必要资源，不把通用 GUI、额外 Agent 子进程或复杂工程模板作为前置依赖。若后续确需生态工具，再评估接入方式。

固定使用一个经过验证的 MaaFramework 版本，并记录截图、鼠标和键盘方式。Win32 有多种输入与截图方法，不假定它们都适配崩铁，也不承诺后台模式必然可用。

## 4. 根据游戏流程组织观察

货币战争包含模式与职级选择、开局情报与投资环境、备战运营、投资策略、补给、遭遇、战斗、奖励处理和整局结算。

需要保留三个不同概念：

| 概念 | 例子 | 含义 |
|---|---|---|
| 当前进度 | `2-7` | 游戏中的位面和节点编号 |
| 节点类型 | 首领、奖励、补给 | 当前节点的玩法属性 |
| 当前界面 | 备战、选择、战斗、结算 | 眼前实际能进行的交互 |

例如：当前是首领节点，但眼前可能正在处理武装箱选择，不能只根据「首领」判断下一步要出战。

流程控制按实际识别结果推进：

```text
识别当前界面
  ├─ 开局或玩法选择 → 返回内容，等待 AI
  ├─ 备战           → 返回局势，等待 AI 操作
  ├─ 战斗           → 监测，等待结束
  ├─ 无选择的掉落   → 收集、更新观察
  ├─ 容器或特殊弹窗 → 读取内容，按是否需要选择决定交回 AI
  ├─ 整局结束       → 读取结算，结束本局
  └─ 无法识别       → 保留现场，提供基础观察和截图
```

补给包、投资效果、角色羁绊和消耗品都可能改变局面、产生新选择。节点数量、选择项数量和上阵上限根据当前界面读取；备战与商店的固定槽位编号见第 5.1 节。

以下选择必须属于 AI 模式的决策范围：

- 已有未完成对局时，继续还是放弃。
- 遭遇节点选择哪个挑战及其风险收益。
- 战斗表现不佳后继续补强、调整或放弃。
- 投资策略与角色效果触发的额外选择。

局外优势布局、图鉴与积分奖励管理可以后续补充，不作为跑通一局的前置开发范围。读取已生效的优势和规则时，应将其对当前动作的影响反映在实际观察中。

### 4.1 备战界面观察草案

依据用户提供的备战截图及其说明：右侧球体是可点击的奖励，底部是角色槽位，角色卡片右上角的白色方框表示前后台。以下是这一张截图的观察与拟定流程；新版是否沿用、不同状态下的表现和具体交互仍待实机确认。

| 区域 | 优先读取 | 用途与边界 |
|---|---|---|
| 顶部 | 备战阶段、进度、生命值，以及可辨认的节点 | 区分当前界面、进度和节点；未识别出的节点不猜测 |
| 中央 | 已上阵数量和上限、前后台槽位及其中角色 | 观察实际站位；固定前台 4 格、后台 6 格，上阵上限另按界面读取 |
| 底部 | 等级、经验、购买经验显示的费用、角色槽位及卡片 | 本图可见 9 个底部槽位、其中 4 张角色卡；按从左到右编号，空位与无法识别分别表示 |
| 角色卡 | 名称或身份、星级、右上角前后台标记 | 据用户说明，上方白色表示可上前台，下方白色表示可上后台，上下均白表示两边均可；不代表当前实际站位 |
| 右侧 | 奖励球、可见物品图标和数量 | 奖励球按当前观察提供位置；图标含义与交互结果未确认时不推测 |
| 右下 | 金币、商店入口、出战按钮 | 读取可见数值和入口；打开商店后再识别商店内容，不将入口当成商店槽位 |

单次备战观察使用同一张截图：先判断是否处于可观察的备战画面，再读取上述区域，最后发布同一帧的截图和识别结果。名称、数值或空位无法确认时标记未知；未打开的商店和详情不报告为没有内容。奖励球可能有多个，需按本次画面定位，不能根据旧截图继续点击。

#### 商店收起与展开

用户提供的样例中，点击右下角带金币数量的「商店」入口后，上方展开商店，入口文字变为「收起」；商店展开时中央前后台区域的位置和大小与收起时不同。识别时先区分商店状态，再使用对应画面的区域；不得复用另一状态下的槽位坐标。

| 状态 | 需要读取的内容 |
|---|---|
| 两种状态均可见 | 备战席角色及槽位、购买经验入口及显示费用、金币数量、中央前后台及上阵数量、右侧装备栏 |
| 收起 | 商店入口及其当前金币数量；有奖励球时另行定位 |
| 展开 | 从左到右识别五张可见商店角色卡的名称和实际价格，分别对应 `shop_1` 至 `shop_5`；读取刷新入口和显示的刷新费用 |

商店截图中还可见角色卡右上角的前后台标记、试用标签、角色词条，以及锁定图标。前后台标记按上表解释；试用标签的作用和锁定图标的具体状态表现待确认。商店固定五格；标价 1 和刷新费用 2 是该样例的内容，不作为固定规则。

观察不自动打开商店或购买。需要商店信息时，由调用方明确要求打开商店，操作后重新截图并发布新的观察；刷新由 AI 明确决定，每次只执行指定的一次并重新识别，不沿用刷新前的角色槽位。入口、展开状态及动作完成特征仍需实机验证后实现。

处理奖励时，先观察并确认目标，再按明确的动作边界点击；点击后重新观察，确认奖励是否收取以及是否出现选择。奖励球收取是否总是无需决策、不同球的区别、成功特征和点击后可能出现的界面均待实机确认，在确认前不自动连续收取。出现选择时交由 AI 决定。

可提前准备界面定位、同帧识别、槽位编号和未知值处理；购买、部署和奖励收取的完成判断，需要收集操作前后样例并核对实际行为。除已确认的固定槽位数量外，截图中的数值和角色只代表该次画面。

## 5. 槽位与目标格式

### 5.1 槽位名称

| 区域 | 名称 | 例子 |
|---|---|---|
| 前台 | `front_N` | `front_1` |
| 后台 | `back_N` | `back_1` |
| 备战席 | `bench_N` | `bench_1` |
| 商店 | `shop_N` | `shop_1` |
| 装备与道具库存 | `bag_N` | `bag_1` |
| 当前选择框 | `option_N` | `option_1` |

根据用户确认，备战和商店槽位数量固定：前台 `front_1` 至 `front_4`，后台 `back_1` 至 `back_6`，备战席 `bench_1` 至 `bench_9`，商店 `shop_1` 至 `shop_5`。这些数量和编号在代码中直接定义；它们不等于当前上阵上限，也不代表所有格子当前都有角色。

约定：

- 编号从 **1** 开始。
- 按当前画面从左到右、从上到下编号。
- 库存和选择框的当前可见数量由观察结果决定。
- `bag_N` 指当前可见的库存格；滚动、排序或布局改变后重新观察。
- 角色身上的装备使用父槽位和装备栏编号，例如 `front_1.equipment_2`。
- 同名角色通过所在槽位区分，不维护持久实例身份。
- 移动、交换、自动升星和角色替换后，以新观察中的槽位为准。
- 空位用 `null`，表示已经确认是空的。
- 无法确认的槽位用 `{"unknown": true}`，不视为空位。
- 未打开或未观察的区域可以不返回，缺失不能理解为没有内容。

角色的实际站位和赋能适用站位是不同信息。程序只按游戏实际限制判断能否操作，不把策略推荐当成硬性合法性限制。

### 5.2 槽位对象

角色保留名称、星级和装备。商店条目增加实际价格。库存物品保留名称及识别到的必要属性。

```json
{
  "front_1": {
    "name": "阿格莱雅",
    "stars": 2,
    "equipment": ["轮滑鞋"]
  },
  "front_2": null,
  "bench_1": {
    "name": "阿格莱雅",
    "stars": 1,
    "equipment": []
  },
  "shop_1": {
    "name": "藿藿",
    "stars": 1,
    "price": 1
  },
  "bag_1": {
    "name": "反重力皮靴"
  },
  "bench_3": {
    "unknown": true
  }
}
```

`equipment` 按角色详情中的装备栏顺序排列，栏位编号从 1 开始。明确的空装备栏可以填 `null`；未能读取完整装备信息时须标记未知，不能用空数组假装没有装备。

第一版名称直接使用游戏中的中文名称。重复库存物品通过槽位区分。只有界面确实显示堆叠数量时才返回 `count`。

## 6. 观察结果

### 6.1 核心观察格式

采用扁平 JSON，字段按当前界面提供，不要求每次输出所有空字段。

```json
{
  "result": "success",
  "screen": "备战",
  "stage": "1-3",
  "node_type": "战斗",
  "hp": 80,
  "gold": 24,
  "level": 5,
  "experience": {"current": 2, "required": 8},
  "deployment": {"used": 2, "limit": 5},
  "refresh_cost": 2,
  "free_refreshes": null,
  "shop_locked": false,
  "slots": {
    "front_1": {"name": "阿格莱雅", "stars": 2, "equipment": []},
    "front_2": null,
    "back_1": {"name": "藿藿", "stars": 1, "equipment": []},
    "bench_1": null,
    "shop_1": {"name": "阿格莱雅", "stars": 1, "price": 1},
    "bag_1": {"name": "反重力皮靴"}
  },
  "unknown": ["free_refreshes"],
  "needs_ai": false
}
```

上例只展示部分槽位，不代表固定布局和当前版本完整数值。`level` 专指团队等级，`deployment` 专指实际已上阵数量与上限。

补充规则：

- 数值字段的 `null` 表示未知，并可在 `unknown` 中列出字段路径。
- `slots` 中直接为 `null` 的值专指确认空位，含义不同。
- 当前有投资环境、投资策略、羁绊、敌人或词缀信息时，按实际决策需要增加对应字段，不预设庞大对象结构。
- `available_actions` 可以列出当前程序已支持且条件允许的封装动作；不把它当成通用输入能力的完整列表。
- 不同画面读取到的信息若可能过期，需要重新核对；恢复操作前不能只信旧缓存。

### 6.2 观察与连续操作

一个 AI 顺序调用命令。调用方根据最新返回的观察决定下一步，服务在操作期间拒绝并发请求。操作后返回新观察或可用截图，元素框和槽位以该次观察为准。

命令超时后先查询服务状态并重新观察，再决定下一步。购买、刷新等操作可能已经生效，不能直接重发。

### 6.3 选择框

选择框需要表达来源、当前选项、选择数量和刷新能力。选项仍用槽位引用。

```json
{
  "result": "success",
  "screen": "选择",
  "choice": {
    "title": "请选择投资策略",
    "source": "投资策略",
    "select_count": 1,
    "refresh_scope": "option",
    "refreshes_left": 1
  },
  "slots": {
    "option_1": {"name": "策略甲", "text": "当前界面识别到的完整效果文字"},
    "option_2": {"name": "策略乙", "text": "当前界面识别到的完整效果文字"}
  },
  "needs_ai": true
}
```

选项数量、费用和刷新方式以当前界面为准。需要不同选择数量、费用或多步骤确认时，补充对应字段；未知时不推测。

## 7. CLI 主命令

以下命令均为设计接口，暂沿用 `m7a cw` 记法说明操作；它不代表独立程序必须由 `m7a.exe` 启动。独立程序实际的可执行文件名和命令入口待确定，届时统一替换示例。

| 命令 | 职责 |
|---|---|
| `m7a cw start` | 启动常驻执行程序，进入 AI 控制模式 |
| `m7a cw status` | 查询运行情况、当前操作、是否等待 AI 或发生异常 |
| `m7a cw observe` | 获取最新界面、局势和目标引用 |
| `m7a cw screenshot` | 获取全窗口或指定区域截图，并返回文件路径 |
| `m7a cw act ...` | 执行封装动作或基础输入 |
| `m7a cw resync` | 废弃失效动态缓存，重新识别并核对局势 |
| `m7a cw resume` | 校验后继续中断的意图，或报告已完成／需要重规划 |
| `m7a cw stop` | 停止控制程序并释放输入，不直接放弃游戏对局 |

```powershell
m7a cw start --json
m7a cw observe --json
m7a cw observe --target front_1 --detail --json
m7a cw observe --wait 30 --json
m7a cw screenshot --json
```

- `start` 建立控制入口，不隐式放弃旧局或直接开启新对局。初次观察让 AI 决定继续旧局或新开。
- `observe --detail` 可以让程序打开并读取目标详情，必要时回到原界面。若产生新选择，立即返回。
- `observe --wait 30` 最多等待 30 秒，直到出现新的可决策局面或异常。等待到期返回当前状态，不视为游戏任务失败。
- 截图返回可供 AI 打开的本地绝对路径，默认截图范围限于游戏窗口。
- 命令行 JSON 输出走标准输出，诊断日志走标准错误或文件。
- 文本统一 UTF-8。机器结果不得夹杂横幅、进度动画或自由格式提示。
- 延续项目已有退出码习惯：0 表示命令按约定完成，1 表示执行失败或结果不确定，2 表示参数错误；已有忙碌、提权失败等约定可以复用。
- 等待 AI 选择属于正常返回；具体操作是否完成，必须读取 JSON 的 `result` 和说明，不能只看退出码。

## 8. 封装动作

### 8.1 通用输入约定

- `--from`：来源槽位。
- `--to`：目标槽位。
- `--options`：选择框中的一个或多个选项。
- 需要复杂参数时支持 `--request-file` 读取 JSON，避免命令行转义问题。
- `resume` 在程序内重新观察并核对原操作的结果，再决定能否继续原意图。

### 8.2 动作清单

| 动作 | 输入示例 | 完成条件与边界 |
|---|---|---|
| `new-run` | `--game-mode normal --difficulty current` | 按明确模式与难度新开一局；已有未完成对局时拒绝隐式覆盖；遇到开局选择即返回 |
| `continue-run` | 无目标槽位 | 从已有对局继续；读取真实当前位置，不假定在备战 |
| `buy` | `--from shop_1` | 检查实际价格与容量，购买后确认商店、金币及阵容变化 |
| `sell` | `--from bench_1` | 确认来源角色与实际出售结果 |
| `refresh` | 无目标槽位 | 刷新一次商店并返回新内容；使用实际刷新费用 |
| `lock-shop` / `unlock-shop` | 无目标槽位 | 验证商店锁定状态 |
| `buy-experience` | 无目标槽位 | 购买一次经验，读取真实花费、经验与等级变化 |
| `move` | `--from bench_1 --to front_2` | 指定来源与目标；目标为空时移动，目标有角色时交换，验证结果 |

| `abandon-run` | 无目标槽位 | 明确放弃并结算整局，读取结果 |

具体交互未适配的动作应明确返回尚不支持，不能用不可靠的默认点击代替。

#### 移动角色的验证草案

`move` 由调用方明确指定角色所在槽位和目标槽位，来源与目标只允许使用 `bench_N`、`front_N`、`back_N`；商店的 `shop_N` 用于购买，不参与 `move`。目标为空时移动，目标有角色时交换；备战席两张不同卡片相互交换已实机验证，其他区域组合待验证。完整封装执行前应重新观察备战界面，确认来源角色、目标内容、当前上阵数量和目标区域；卡片上的上下白色方框按第 4.1 节说明读取，未知时不据此推断允许位置。商店展开与收起时站位区域不同，不能沿用旧坐标。

确认条件后拖动一次，再观察来源、目标和上阵数量等可用证据。只有确认角色确实到达目标才能报告移动成功；点击或拖动任务完成本身不代表游戏接受操作。无法核对结果或出现新选择时停止并返回现场，不自动重试。具体完成特征、画面稳定时机和特殊角色行为仍需实机验证后实现。

**当前实现是需要人工核对的基础槽位拖动**：`tools/cw.py act move --from bench_1 --to bench_2` 按商店收起时的 1920×1080 固定坐标拖动一次，并返回截图和 `uncertain`；尚不识别当前界面、角色、槽位占用或动作结果。调用方必须先查看最近一次截图，确认处于商店收起的备战界面、来源和目标符合意图；操作后通过新截图确认结果，不自动重发。其他尺寸会拒绝执行。接口 `POST /move` 接收 `from` 和 `to`，不接受商店槽位或相同的来源与目标。

实机样例：在 1920×1080、商店收起的备战界面，同等提权下通过基础坐标拖动分别将备战席第 1、2 格的角色移入后台第 1 格和前台第 1 格；后续截图显示来源格清空、目标出现角色，上阵数从 0/3 依次变为 1/3、2/3。另一次拖动备战席两张不同卡片，后续截图确认两者位置交换。后台拖动后立即截图仍是过渡画面，不能把该帧当作最终结果；自动验证尚未实现。

```powershell
m7a cw act buy --from shop_1 --json
m7a cw act move --from bench_3 --to front_2 --json
m7a cw act equip --from bag_1 --to front_1 --json
m7a cw act choose --options option_2 --json
```

请求文件中的字段与命令行含义一致：

```json
{
  "action": "equip",
  "from": "bag_1",
  "to": "front_1"
}
```

```powershell
m7a cw act --request-file decision.json --json
```

第一版不支持开放式批量脚本，也不让程序自行选择购买对象或阵容。后续可增加明确预算与停止条件的快捷操作，例如限次搜卡和目标阵容部署。

### 8.3 购买角色：详细设计草案

本节示范一个动作需要说明到什么程度，供人工审阅与后续实现。界面布局、售出标记、费用变化和自动升星的实际表现均需用目标版本实机确认；在确认前，下面的判断是拟定规则，不表示当前小助手已经这样实现。其他动作仍需分别补充同等清晰的设计，不能直接套用购买的判断条件。

#### 目标与整体流程

AI 指定当前商店的一个槽位，程序最多尝试点击购买一次，确认结果后返回。程序不自行决定买谁、不刷新商店，也不为了腾位置自行出售角色。

```text
AI：购买 shop_1
  → 从最近一次观察读取 shop_1 的角色、价格和金币等条件
  → 保存购买前的必要信息
  → 点击一次 shop_1
  → 等待购买结果或意外弹窗
  → 核对金币、目标商店格及必要的角色变化
  → 返回成功、失败或不确定，并附最新观察
```

#### 点击前检查什么

1. 服务在操作入口拒绝并发输入。
2. 从最近一次观察读取商店状态、指定格的角色名称、实际价格和可用状态。没有可用观察或目标不明确时，不点击。
3. 读取当前金币，确认价格和金币均可靠可读、金币足够。金币或实际费用不明时不猜测价格，不点击。
4. 检查当前是否允许接收该角色，例如位置已满或游戏提示不可购买。**位置已满时是否允许通过自动升星购买，以及如何提前可靠判断，待实机确认**；不能确定时不点击，返回原因供 AI 处理。
5. 保存本次判断需要的购买前信息：角色名称、目标商店格、实际价格、金币，以及可可靠读取且与验证相关的角色状态。具体识别不到的内容记为未知，不用上一次的猜测代替。

如果检查失败发生在输入之前，结果为 `failed`，说明未点击及原因；需要重新决策或人工处理时设置 `needs_ai: true`。有可用观察时随结果返回。

#### 点击后怎么判断

只点击一次，等待与购买有关的画面变化，并设置有限截止时间。这里检查的是商店格、金币或相关提示，不要求整个游戏画面静止。截止时间、识别阈值和售出标记以实机样例验证后确定，不在本草案中编造数值。

假设购买前金币为 24、页面确认实际价格为 3，那么正常扣费情况下，购买后预期金币为 **21**。但金币减少本身只能证明货币变化，不能单独证明买到了指定角色。首版拟采用以下保守规则：

| 购买后的可靠观察 | 返回 | 处理 |
|---|---|---|
| 金币减少额等于购买前确认的实际价格，且目标商店格出现经实机验证的售出／已购买标记 | `success` | 认为本次购买已确认；重新读取相关局势 |
| 上述金币和商店格证据成立，并观察到角色新增或升星 | `success` | 同时返回可靠识别到的新角色状态；不可用旧槽位推测最终位置 |
| 金币有预期变化，但商店格无法确认；或者商店格有变化，但金币无法确认 | `uncertain` | 保存已知证据，停止，不重复购买 |
| 金币变化与预期不符，或识别结果互相矛盾 | `uncertain` | 停止并返回实际观察；可能有特殊规则、界面变化或识别错误 |
| 发出点击后出现未知弹窗、画面离开预期界面或等待到期，无法确认购买结果 | `uncertain` | 停止后续操作，保留现场与必要截图，交给 AI 判断 |
| 发出点击后，游戏明确显示不能购买，且能可靠确认购买未发生 | `failed` | 返回已识别的原因和最新观察，不自动重试 |

金币和商店格都没变化，也**不能仅凭这一点断言点击没有生效**：画面可能尚未更新或识别可能失败。超过截止时间仍无法确认时返回 `uncertain`。免费购买、折扣、返还金币或特殊效果是否存在、如何验证，必须在目标版本实机确认；不满足上述正常扣费规则时，先返回不确定，不能硬判成功。

若购买触发自动升星或额外选择，角色槽位可能变化：重新识别相关区域；出现需要玩法决策的弹窗就停止并交给 AI。角色状态未读全时明确标为未知，不伪造新位置或星级。购买已被可靠确认但后续选择尚待处理时，购买结果可以为 `success`，同时 `needs_ai: true`；若购买本身仍无法确认，则为 `uncertain`。

#### 返回示例

以下数字仅用于说明格式，不代表实际游戏费用。`evidence` 记录本次验证依据，不替代最新 `slots` 观察；商店格变化的具体名称须在实机验证后确定。

```json
{
  "result": "success",
  "screen": "备战",
  "needs_ai": false,
  "action": "buy",
  "from": "shop_1",
  "message": "已确认购买藿藿。",
  "evidence": {
    "name": "藿藿",
    "price": 3,
    "gold_before": 24,
    "gold_after": 21,
    "shop_slot": "已售出"
  },
  "gold": 21,
  "slots": {
    "shop_1": null,
    "bench_1": {"unknown": true}
  }
}
```

示例中 `shop_1: null` 表示已确认该格为空；若游戏实际显示的是售出标记而非空格，须按实际设计表达，不能强行使用 `null`。`bench_1` 未识别时保持未知；示例不声称角色一定进入该位置。

不确定时也返回事实，例如：

```json
{
  "result": "uncertain",
  "screen": "备战",
  "needs_ai": true,
  "action": "buy",
  "from": "shop_1",
  "message": "已点击一次；金币从 24 变为 21，但无法确认商店格状态，请先检查局面。",
  "evidence": {
    "name": "藿藿",
    "price": 3,
    "gold_before": 24,
    "gold_after": 21,
    "shop_slot": "未知"
  }
}
```

AI 看到 `uncertain` 后应先查看新观察或截图；必要时执行 `resync`。不能因为命令没有返回 `success` 就直接再买一次。

## 9. 通用界面操作与截图兜底

这是封装覆盖不足时的备用能力，不要求每个新弹窗都先有专用动作。

### 9.1 基础观察

程序提供可见文字、元素框，以及可靠识别到的角色和装备名称。基础元素引用以最近一次观察为准。

```json
{
  "result": "success",
  "screen": "未知",
  "needs_ai": true,
  "image_size": [1920, 1080],
  "elements": [
    {"ref": "e1", "text": "确认选择", "box": [1420, 570, 140, 50]},
    {"ref": "e2", "text": "取消", "box": [1220, 570, 140, 50]}
  ],
  "screenshot": "C:/game/debug/s58.png"
}
```

- `box` 统一为 `[x, y, width, height]`。
- 坐标相对于返回的游戏窗口截图，左上角为原点，单位为该截图像素。
- 程序内部负责截图像素到实际输入坐标的转换，包括窗口偏移和 DPI 缩放。
- 识别框、截图和基础输入统一采用 MaaFramework 适配层约定的坐标空间；不可混用未经转换的桌面坐标、原始窗口坐标和缩放后的识别坐标。
- 返回截图尺寸，供坐标操作核对。
- OCR 识别到文字不代表它一定可点击，不虚构可交互属性。
- 对遮挡、重复文字和未知图标不作无依据判断，需要时让 AI 看图。

### 9.2 基础动作

| 动作 | 示例 |
|---|---|
| 点击 | `act click --target e1` |
| 双击 | `act double-click --target e1` |
| 拖动 | `act drag --from e3 --to e8` |
| 坐标点击 | `act click --x 900 --y 600` |
| 坐标拖动 | `act drag --from-x 900 --from-y 300 --to-x 700 --to-y 500` |
| 滚动 | `act scroll --target e3 --direction down --steps 1` |
| 按键 | `act press --key escape` |
| 输入文字 | `act input --text "内容"` |

**当前已实现：坐标单击。** 使用 `tools/cw.py act click --x 100 --y 70`，服务以 MaaFramework Win32 `Seize` 前台鼠标方式发送一次左键单击，并立即重新截图、返回文件路径。此方式会占用鼠标；目标窗口及其输入方式的游戏兼容性待实机确认。坐标必须落在最近一次截图的宽高范围内，窗口缩放或尺寸改变后的对应关系仍须重新观察核对。

单击任务和后续截图均成功时返回 `success`，仅表示输入任务完成并获得新截图，不代表游戏接受了点击或达成业务结果。点击任务失败或点击后截图失败时返回 `uncertain`，应先重新截图检查现场。没有可用的截图尺寸或坐标越界时返回 `failed`，不会发送输入。内部接口为 `POST /click`，CLI 发送的 JSON 请求体为 `{"x": 100, "y": 70}`；无参数命令发送空对象。

**坐标拖动与按键：** `tools/cw.py act drag --from-x 100 --from-y 100 --to-x 300 --to-y 200 --duration 500` 使用左键拖动；时长单位为毫秒，默认 500，允许 1 至 10000。拖动起点和终点都必须在对应截图范围内。`tools/cw.py act press --key escape` 按下并释放一个键；支持 `escape`、`enter`、`space`、`tab`、`backspace`、`left`、`up`、`right`、`down`、字母 `a` 至 `z` 和数字 `0` 至 `9`，不支持组合键。键名不区分大小写。

对应 HTTP 接口是 `POST /drag`（字段 `from_x`、`from_y`、`to_x`、`to_y`、`duration`）和 `POST /press`（字段 `key`，键名使用小写）。鼠标和键盘均使用 MaaFramework `Seize` 前台输入方式。两种动作都在执行一次后立即截图并返回文件路径；输入或后续截图失败返回 `uncertain`，不自动重发。拖动和按键目前只经独立测试窗口验证，游戏兼容性待实机确认。输入法可能改变字母键在普通文本窗口中的表现，本接口不提供文字输入。

基础输入前，程序必须暂停原封装流程并取得独占操作权；暂时不能停止的步骤返回忙碌，不并行操作。基础输入之后，原有动态观察失效。

截图只是观察，不隐式关闭弹窗或替 AI 选择。使用基础动作修正界面后，通过 `resync` 重新核对，再判断能否 `resume`。

## 10. 执行结果与三类处理状态

### 10.1 操作结果

| `result` | 含义 |
|---|---|
| `success` | 已确认达到本次命令承诺的结果 |
| `failed` | 已确认未完成，或前置条件不满足而未执行 |
| `uncertain` | 操作可能已生效，但无法可靠确认 |

结果与是否需要 AI 继续决定是两回事，使用可选的 `needs_ai` 表达。普通可靠备战观察可省略该字段；出现新选择或需要接管时设为 `true`。

若封装动作中出现额外选择，返回 `needs_ai: true` 和已完成步骤；最终效果尚未验证时使用 `uncertain`，并明确是等待决策，不暗示要重做已完成动作。

```json
{
  "result": "uncertain",
  "screen": "选择",
  "needs_ai": true,
  "action": "equip",
  "message": "已完成拖动，出现装备替换选择，最终穿戴结果尚未确认。",
  "completed_steps": ["定位库存物品", "定位前台第1格", "拖动"],
  "choice": {"title": "选择替换装备", "select_count": 1}
}
```

动作返回时尽量附带最新局势，减少额外的 `observe`。返回内容不得宣称尚未验证的成功。

### 10.2 三类处理状态

| 类别 | 触发条件 | 行为 |
|---|---|---|
| 正常执行 | 程序认识界面，能执行明确意图 | 按封装流程操作并验证 |
| 需要 AI 接管 | 正常玩法选择，或未覆盖界面 | 返回内容、文字、元素与必要截图，等待 AI |
| 执行异常 | 已有流程未达预期、超时或进入意外界面 | 停止后续操作，保存上下文，交给 AI 排查 |

后二者共用接管能力。执行异常额外说明原意图、已确认完成步骤、预期结果和实际画面。

「页面没切换」不是唯一异常标准。购买可能不切页面，战斗动画可能一直变化但实际未推进。判断依据应是每个动作自己的完成条件。

## 11. 异常恢复协议

```text
正常执行
   ↓ 失败、超时、未知界面
暂停后续动作，释放按住的鼠标和按键，保存现场
   ↓
AI 读取上下文，按需获取截图
   ↓
AI 使用基础点击、拖动、按键修正界面
   ↓
resync：重新识别页面和局势
   ↓
resume：先检查原目标结果
   ├─ 已完成 → 返回成功
   ├─ 条件仍满足 → 从可验证步骤继续
   └─ 目标或局势改变／仍不明确 → 返回新局势，由 AI 重规划
```

恢复要求：

1. **单一操作权。** AI 接管时原流程不得继续点击。
2. **动态缓存失效。** 旧坐标、商店、角色位置、装备和选项必须重新核对。
3. **先确认结果，再决定重试。** 购买后识别失败可能实际已购买并自动升星，不能再次点击花钱。
4. **从真实状态重新进入。** 不依赖报错前的代码行号或旧节点编号。
5. **`resync` 不代替策略。** 它不擅自出售角色、放弃对局或选择奖励，也不默认按 ESC 清理未知界面。
6. **`resume` 不能直接重放原命令。** 恢复前验证原意图是否已完成，以及剩余动作是否仍有意义。
7. **等待 AI 不算卡死。** 可以监测连接状态，但不能因等待接管就自动放弃游戏对局。
8. **恢复尝试必须有界。** 仍无法确认时保留现场并返回，不能无限循环点击。

最小日志内容：原指令、操作前后状态、关键步骤、确认到的变化、错误说明，以及必要截图路径。

## 12. 操作封装、Pipeline 与页面导航

常见动作可组织成小型的识别驱动流程：

```text
检查前置条件 → 定位 → 动作 → 等待稳定 → 验证
                       │                  │
                       └────异常或新选择──┘ → AI 接管
```

- 页面导航解决「当前在哪，怎样到目标页面」。
- 操作流程解决「怎样完成这次已明确的动作」。
- AI 负责玩法选择和流程未覆盖的情况。
- 恢复时重新识别当前页面，并检查业务结果；回到正确页面不等于业务动作尚未完成。

采用 MaaFramework 承担识别和动作执行，但每个 Pipeline 只完成一项范围明确的操作或一次页面切换。

例如：

```text
购买：识别商店与目标 → 点击购买 → 验证金币、商店与阵容变化
装备：识别来源物品 → 定位角色 → 拖动 → 检查装备结果或新选择
导航：识别当前位置 → 执行已知页面切换 → 确认目标界面
```

具体规则：

- 不用一个覆盖整局的巨型 Pipeline 固定所有玩法决策。
- AI 指定槽位后，Python 将其转换成短任务的识别区域、目标与必要参数。
- 可配置的界面识别和机械步骤放入 Pipeline；局势汇总、条件判断和跨动作恢复保留在 Python。
- 通过独立识别／动作接口支持基础观察和 AI 兜底，不要求所有临时操作都预先有专用 Pipeline。
- 已知纯机械异常可以使用明确的异常分支处理；新玩法选择或未覆盖界面返回 Python 并交给 AI。
- 不在自定义动作回调中长期等待外部模型，避免一个任务一直占用执行链。
- `post_stop` 是停止能力，不是保存执行栈的暂停。接管前等待停止确认、释放输入；恢复时重新识别并提交合适的短任务。
- 任务执行状态、页面到达状态和业务完成状态分别核对，防止把「点击执行成功」误认为「装备已经穿戴」。

## 15. 开发顺序与验收

### 先明确速度目标与优化顺序

性能目标：常见局面快速识别、常见意图短链路执行，异常场景允许进入较慢的补充识别和 AI 接管。速度与识别准确率同时验收，不能通过猜角色或跳过结果验证来缩短耗时。

整段耗时拆成：

```text
CLI 启动／通信 + 截图 + 局面识别 + AI 决策 + 输入操作 + 游戏响应等待 + 结果验证
```

分别计时，先解决实际占比最大的部分。CPU 图像匹配、界面等待和模型响应不能混成一个耗时后直接归因于 Python。

首批试验可使用以下**待验证的工程目标**，不是现有实测成绩，也不承诺任意电脑都能达到：

| 测量范围 | 初始目标 | 计时边界 |
|---|---|---|
| 常规商店观察 | P95 不超过 1 s | 常驻服务收到请求后，截图、OCR 读取可见角色名称与价格、必要数字识别、生成 JSON；不含外部 AI 和 CLI 启动 |
| 无文字槽位的头像匹配 | 预算待真实样例基准确定 | 仅用于不能直接读取名称的角色区域，独立统计耗时；不作为商店识别的默认路径 |
| 识别质量 | 标注样例集内不接受错认；模糊样例可返回未知 | 同时记录正确识别率、错认数和未知比例，不能靠大量拒识掩盖覆盖不足 |

先在目标电脑上测量，再确认最终预算。整局识别全部角色、首次加载、打开详情面板、异常恢复另列统计，不能套用五个商店槽位的预算。候选素材数量也必须随结果记录。

#### 首个可测原型：商店名称 OCR 与购买闭环

商店本身显示角色名称，首选读取文字，不要求先准备完整头像模板库。输入是一组真实商店截图；输出是各商店槽位的名称、价格、金币或未知，以及单独保存的耗时记录。

当前有独立的离线试验脚本 `tools/ocr.py`，使用 CPU 推理，读取图片和指定的 MaaFramework OCR 模型目录，输出原始文字、识别框、置信度、耗时及进程内存，不连接游戏，也不解析为商店槽位。例如：

```powershell
.\.venv\Scripts\python.exe tools/ocr.py <图片路径> <模型目录> --roi 340 55 1370 285
```

`--roi` 使用输入图片的像素坐标，上例仅适用于本次测试截图，不能当作通用商店区域。`--repeat 10` 在同一进程中对同一张图片实际识别 10 次，分别返回每次结果与耗时；同图重复测量不代表不同画面的识别准确率。模型目录需要 `det.onnx`、`rec.onnx`、`keys.txt`；测试时使用的本机模型副本在忽略提交的 `tools/.runtime/ocr-model/`，发布所需模型来源和授权待确认。该脚本只用于离线试验，尚未接入常驻服务。

1. 先标注少量商店截图，覆盖正常名称、低清文字、相似名称、售空格和过渡画面。
2. 使用一张内存截图读取所有当前商店条目；同帧 OCR 结果按文字位置归入槽位，不为每个名称重复截屏和识别。
3. 名称识别与数值识别按需要使用局部区域；识别结果可对照目标版本名称表校验，无法区分时返回未知，不强行纠正成最接近的角色。
4. 先离线测量 OCR，再接实时截图，分别统计截图、OCR、解析与总观察耗时。
5. 接入一次购买，检查金币、商店及角色变化，动作后直接返回新局势。
6. 记录自动升星、库存变化或新弹窗引起的额外验证开销。

一百次以上的热运行可用于初步延迟测量；正确率评估仍取决于标注截图的质量与覆盖范围。不能用缓存同一张截图的结果代替真实 OCR 测量。

无可读名称的前后台头像、备战席角色和装备库存另做识别基准。若使用半图模板，需要按界面布局预裁、预缩放并缓存，对齐有效区域；比较最佳与次佳候选，低置信度再打开详情或交给 AI。合成遮挡样例只能作为真实截图的补充。

#### 正常执行路径优先优化

- 一次观察返回当前决策真正需要的信息，动作结果直接附新局势，减少额外的 CLI 与 AI 往返。
- 常见角色与装备优先使用当前画面的快速识别，低置信度时才打开详情、OCR 或交给 AI 看图。
- 有明确槽位时缩小识别区域，不在全屏反复搜索每张头像。
- 识别模型、素材和必要的预处理结果常驻内存，Python 不逐像素处理图片，计算交给 MaaFramework／OpenCV 等原生实现。
- 根据操作影响范围重新识别；购买可能触发升星，装备和角色效果可能触发弹窗，此时必须扩大核对范围。
- 缓存复用需要确认区域和上下文仍有效；AI 基础输入、重新同步和意外弹窗后废弃相关动态缓存。
- 等待以具体结果、相关区域稳定和截止时间为依据；不要给每一步叠加较长固定休眠，也不能把所有等待机械地设为零。
- 截图是否稳定只检查相关区域，避免装饰动画导致整屏永远不稳定。
- 阈值和速度调优使用同一份标注截图回归，保留实际失败样例。

#### 什么时候才引入自定义 C++

先使用 Python 主控与 MaaFramework 原生识别。若实测仍未达到预算，先检查截图、重复识别、任务调度、文件加载和固定等待。

当耗时分析证明大量 Python 小调用、数据转换或候选循环已成为主要瓶颈时，再考虑把整批头像识别器做成 C++ 模块。使用相同输入、候选库、阈值与准确率要求比较结果。只迁移明确的热点，不因图像处理听起来复杂就重写整个项目。

后续可增加由 AI 明确指定的组合操作来减少往返，例如一次提交最终站位或带预算的搜卡。组合操作逐步校验；出现新玩法选择、目标变化或结果不确定立即返回已执行内容，不承诺整体回滚。首版先验证单动作闭环。

### 阶段零：MaaFramework 实机兼容性验证

先以最小 Python 程序验证：

1. 找到崩铁窗口，稳定获取画面，并核对分辨率、DPI 和坐标转换。
2. 完成一次 OCR／模板定位、普通点击和装备或角色拖动。
3. 运行一个短 Pipeline，停止后确认不再输入；通过同一适配出口执行基础操作，再重新观察并提交新任务。

验收记录包含 MaaFramework 版本、截图方式、鼠标／键盘方式、权限、游戏窗口模式和实际结果。先证明前台可靠操作，再按需要验证后台或云游戏。验证未通过时，明确兼容性缺口，集中调整控制适配层。

### 阶段一：框架和格式

- 实现 CLI、本地通信、常驻执行入口和 MaaFramework 资源／控制器／任务执行生命周期。
- 固定槽位、观察、结果、基础元素和日志格式。
- 使用固定样例局势，不模拟完整游戏规则。
- 跑通观察、提交动作、返回新观察和异常接管。

验收：AI 能按协议操作；输入不并发；操作结果与新截图一同返回。

### 阶段二：接入已有游戏能力

- 通过 MaaFramework 识别与 Python 汇总，接入备战、金币、商店和角色位置等基础观察。
- 以短 Pipeline 或必要的 Python 自定义动作完成购买、移动、交换、出战和最小结果验证。
- 接入截图、基础输入、`resync` 和 `resume`。

验收：至少完成一轮真实的购买、部署、战斗和结果反馈。

### 阶段三：选择与装备

- 补齐投资、补给、遭遇和道具／角色触发的选择。
- 增加装备、合成、道具使用和相关验证。
- 按实际缺口补素材和规则。

验收：操作触发新弹窗时能够停住交给 AI；AI 处理后可以重新核对并继续。

### 阶段四：完整对局与新版适配

- 覆盖开局、旧局继续、全流程运营、整局结算。
- 接入新版素材、布局、规则与策略。
- 区分节点表现不佳和整局结束，保留必要战斗反馈。

验收场景至少包含：

1. 正常购买成功。
2. 购买触发自动升星，旧槽位变化。
3. 刷新后返回新的商店观察，下一条购买命令使用刷新后的槽位。
4. 移动后触发角色特殊选择。
5. 装备操作出现新选择，AI 处理后恢复。
6. 点击未生效与实际已生效但识别失败，两种情况得到不同处理。
7. 未知弹窗使用截图和基础输入处理。
8. 战斗结束扣血但对局仍可继续。
9. 旧局接管、暂停、停止和重新同步。
10. 服务重启后，坐标输入需要先取得本次会话的截图。

样例通过只能证明接口和控制流程成立；真实游戏操作仍需用现场截图和实机结果验证。

## 16. 开发前待实机确认的事项

- 新赛季的节点流程、槽位布局、装备库存滚动和选择框表现。
- 装备穿戴、合成、拆装以及道具使用的真实完成特征。
- 各种自动升星、特殊单位和额外上阵位对观察的影响。
- 不同分辨率、窗口缩放和云游戏下的坐标映射。
- MaaFramework 在崩铁中的截图、鼠标／键盘方式及停止后的再执行行为。
- 识别详情面板是否会触发特殊选择，以及如何可靠返回原界面。
- 无法完整确认局势时，每个封装动作最低需要哪些已知字段。

未确认内容先保留为不支持或未知，不写成看似可靠的默认行为。
